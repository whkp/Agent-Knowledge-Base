# 检索与策略

AgentKB 如何把一个提问变成证据、有哪些可调项、以及怎么改才不是靠猜。文中数字来自一个 25 页的本地工作区与默认多语言 embedding 模型，请把它们当作标定值而不是常量。

**中文** · [English](RETRIEVAL.md)

## 两条检索路径

| 路径 | 接口 | 检索对象 | 需要 embedding | 需要模型 |
| --- | --- | --- | --- | --- |
| 页面优先 | `POST /api/knowledge-bases/{id}/wiki/query` | `wiki/` 下的 Markdown 页面 | 仅 `hybrid`/`planned` 策略需要 | 仅答案综合与 `planned` 需要 |
| 原始资料 RAG | `POST /api/search` | Chroma 中的 `document_chunks` | 需要 | 仅答案综合需要 |

两者回答的是不同问题。页面优先返回**被维护过的知识**；原始资料 RAG 返回**来源当时到底说了什么**。工作台两条都暴露；MCP 把页面优先暴露为 `query_wiki`，把分块路径暴露为 `search_knowledge_base`。

## 页面优先的完整步骤

1. **读取工作区。** 载入 `wiki/` 下每个可读页面，含标题、摘要、正文与修改时间。
2. **给问题切检索词**（`_search_tokens`）：
   - 拉丁词保持整词并小写（`RAG`、`MLCC`）。
   - 连续汉字切成重叠二元组：`如何配置资产` → `如何 / 何配 / 配置 / 置资 / 资产`。
   - 重复词项合并；单个汉字保持原样。
3. **用 BM25 打分**（`_lexical_scores`）：词频饱和 + 按长度归一化，再除以"所有检索词都出现在该页"时的理想分——所以得到的是 0..1 的"覆盖率"，而不是无上界的加和。
4. **按策略叠加向量**：`relevance = min(1, 词法分 + 相似度 × WIKI_QUERY_VECTOR_WEIGHT)`，其中页面只有在余弦相似度越过 `WIKI_QUERY_VECTOR_FLOOR` 时才算语义命中。
5. **最终页面分**：`0.15 + 0.55 × relevance + 0.30 × 标题覆盖度`，封顶 0.99。
6. **沿链接扩展**：从直接命中出发，受策略的跳数与关联页上限约束，每一跳把继承的置信度减半。以这种方式加入的页面标 `related: true`，并排在直接命中之后。
7. **作答。** 确定性模板用摘要作答。若配置了模型，同一批证据以编号来源送出，答案获得可跳转到页面路径的行内 `[n]` 引用。
8. **可选结晶**：调用方传 `save_as` 时写入 `wiki/queries/<slug>.md`。结晶页面与确定性回答都只使用直接命中。

### 为什么用二元组，以及它修不了什么

子串匹配意味着 `如何配置资产` 在一个满是 `资产配置` 页面的工作区里**什么都找不到**——两者只差语序和一个虚词。二元组正好修掉这一点：

| 提问 | 改造前 | 改造后 |
| --- | --- | --- |
| 资产配置 | 4 命中 | 6 命中 |
| 如何配置资产 | **0 命中** | 6 命中 |
| 检索的策略 | **0 命中** | 2 命中 |
| 怎么分散风险 | **0 命中** | 2 直接 + 2 关联 |
| 小孩子（本工作区没有相关内容） | 0 命中 | 0 命中——正确 |

二元组不是同义词模型。`小孩子` 永远不会找到 `闰土`；那只能靠向量侧，而且只有当工作区里确实存有相关内容时才可能。

### 为什么是 BM25 而不是词频

词频会随问题变长而增长、也随页面变长而增长，于是最长的页面永远赢，短问题失去分辨力。用词频时，四个关于资产配置的页面全都得 0.99，排序退化成按路径字母序。用 BM25 之后：

```text
0.9254  wiki/topics/四个木-2024-年度资产配置总结.md
0.9097  wiki/sources/10-四个木-2024-年度资产配置总结.md
0.8903  wiki/topics/小苏-想退休-资产配置入门.md
0.8668  wiki/sources/11-小苏-想退休-资产配置入门.md
0.3678  wiki/sources/5-ramit-sethi-净资产-流动性与现金流.md
```

主题页现在排在它们所综合的原始来源页之前，这正是期望的方向：被维护过的页面是更好的答案。

### 为什么向量需要下限

Embedding 是稠密的：任何页面与任何问题之间都有*某个*正相似度。没有下限时，`hybrid` 对任何问题都会返回"最不无关"的五个页面——看着像召回，实际是噪声，而且它掩盖了本该诚实说出的「这个工作区回答不了这个问题」。在默认模型上的实测：

| 提问 | 最高相似度 | 页面中位数 | 结论 |
| --- | --- | --- | --- |
| 资产配置 | 0.675 | 0.182 | 真实命中在 0.5 以上 |
| 小孩子 | 0.201 | 0.141 | 无关页面落在 0.1–0.2 区间 |

因此有 `WIKI_QUERY_VECTOR_FLOOR=0.35`。有了它，`小孩子` 返回 0 命中、确定性回答如实说明；而 `退休后怎么安排钱` 从 2 命中 / 0.61 提升到 4 命中 / 0.74。

## 策略

策略的**集合**是代码，策略的**选择**是数据：它随请求发出、随响应返回、随反馈入库，并且正是回放工具用来对比的对象。

| id | 跳数 | 关联页上限 | 向量 | 模型改写 | 何时使用 |
| --- | --- | --- | --- | --- | --- |
| `auto`（默认） | 自适应 | 3 | 否 | 否 | 工作台日常使用；不需要模型与 embedding |
| `local` | 1 | 0 | 否 | 否 | 对比基线：只用直接命中会得到什么 |
| `deep` | 2 | 6 | 否 | 否 | Agent 探索，愿意用精确度换召回 |
| `hybrid` | 自适应 | 3 | 是 | 否 | 提问措辞与页面用词不一致 |
| `planned` | 自适应 | 3 | 是 | 是 | 调用方有模型，且问题比较含糊 |

`auto` 的自适应规则：只有当最高直接命中分低于 `WIKI_QUERY_DEEP_THRESHOLD`（默认 0.5）时才走第二跳。有把握的查询就用已找到的东西作答，而不是乱走；证据不足的查询宁可多花一跳，也不从薄弱的证据上作答。

### 看见到底跑了什么

每个响应汇报的是**实际发生了什么**，而不是被要求了什么：

| 字段 | 含义 |
| --- | --- |
| `strategy` | 实际执行的策略 id |
| `hops` | 实际走过的链接跳数 |
| `vectors` | 页面向量是否参与（被下限全部拒绝或 embedding 不可用时为 false） |
| `planned` | 模型是否提供了额外检索词 |

这四个字段是反馈可被分析的前提：没有它们，一个 👍 或 👎 说明不了**当时被判定的配置**是什么。点「没用」时还可以指认具体哪几条引用不对（`bad_paths`），回放因此能从集合级提问（"当时的引用还在吗"）升级到页面级提问（"被指认的那条还在吗"）。

### 从工作台选择

查询坞里有策略选择器。它选中的值会随问题一起送出，并随评分一起入库，所以一个人可以在 `auto` 失手的问题上试 `hybrid`，这次对比会落进反馈表。

评分写回后可以在工作台的「反馈」纸里读：按时间倒序列出评分、问题、原因、当时的策略与被指认的引用；点问题可以把它填回查询框重跑。这张纸只读，不引入任何新的写路径。

### 从 MCP 选择

```
list_retrieval_strategies()                     # id、名称与取舍
search_with_strategy(kb_id, query, "hybrid")    # 只做检索，绝不调用 Backend 模型
```

MCP 的检索工具仍然强制 `llm.enabled=false`：推理由调用方 Agent 完成，AgentKB 只提供证据。

## 新增一个策略

策略是代码是有意为之——这是防止模型悄悄改掉检索方式的闸门。

1. 在 `backend/app/services/retrieval_strategy.py` 加一条 `RetrievalStrategy(...)`。`hops` 是整数或 `"auto"`；`neighbour_limit` 限制关联页数量；`use_vectors` 与 `plan_query` 打开两个可选阶段。
2. 如果它需要**新行为**（而不只是不同的数字），在 `query_wiki` 里实现该标志并保持确定性：模型只能提供检索词，永远不能提供排序。
3. 加一个测试，证明新策略以预期方式区别于已有策略。
4. 在改动任何默认值之前，先对记录下来的反馈跑 `backend/scripts/replay_queries.py --strategies <旧>,<新>`。丢掉人们点过赞的引用的策略就是回归，无论它的聚合数字多好看。

## 配置项

| 变量 | 默认值 | 作用 |
| --- | --- | --- |
| `WIKI_QUERY_DEFAULT_STRATEGY` | `auto` | 请求未指定策略时使用哪个 |
| `WIKI_QUERY_NEIGHBOUR_LIMIT` | `3` | `auto` 的关联页上限（0 表示不扩展） |
| `WIKI_QUERY_DEEP_THRESHOLD` | `0.5` | 低于该分数时 `auto` 可以走第二跳 |
| `WIKI_QUERY_VECTOR_WEIGHT` | `0.35` | 相似度最多可以在词法分之上加多少 |
| `WIKI_QUERY_VECTOR_FLOOR` | `0.35` | 算作语义命中的最低余弦相似度 |

改这些就是改检索质量，所以请按改策略的同一标准来改：附上一份回放对比。见 [SELF_EVOLUTION_CN.md](SELF_EVOLUTION_CN.md)。

## 成本与失败行为

- **默认路径不加载模型。** `auto` 与 `local` 从不触碰 embedding，所以全新安装无需下载任何东西就能作答。
- **embedding 按工作区缓存**，只有当某个页面的文件时间戳变化时才重建。首次使用付出模型加载成本，之后每次查询只付出一次点积。
- **一切都会降级。** 没有 embedding → `hybrid` 表现得像 `auto` 并上报 `vectors=false`。没有模型 → `planned` 用原问题检索并上报 `planned=false`。两者都不会抛错。
- **打分随页面数量线性增长**，BM25 需要整个语料在内存里——在本项目瞄准的规模下（几十到低几百页）完全够用，这也正是"索引用文件而不是服务"的原因。

## 已知局限

- 没有 embedding 就没有同义词处理；不是多语言模型就没有跨语言匹配。
- 没有学习式排序，没有点击行为信号；唯一的信号是显式的 👍/👎。
- 一跳扩展很便宜，两跳是当前上限。更深的遍历尚未被证明比"把第一跳的召回做好"更有用。
- 回放工具不覆盖原始资料路径：重放它需要向量库与另一种引用格式（`document:<id>#<chunk>`）。
