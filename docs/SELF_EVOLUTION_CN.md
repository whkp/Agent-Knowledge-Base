# 不靠自我改写 Agent 的自进化

AgentKB 里「自进化」指什么、每一步由谁负责、以及为什么这个项目**不**在后端里塞一个 agent。

**中文** · [English](SELF_EVOLUTION.md)

## 先把话说准

AgentKB 在两条轴上进化，而两条轴需要的机器完全不同：

| 轴 | 改进什么 | 信号 | 状态 |
| --- | --- | --- | --- |
| **知识** | wiki 本身：补缺口、合并来源、标注矛盾 | lint 问题、图谱缺口、覆盖率 | 部分自动化（摄取 + 主题页综合），由缺口驱动的研究尚未实现 |
| **检索策略** | 一个提问如何变成证据 | 每次回答的显式 👍/👎 | 闭环已端到端打通（信号 → 回放 → 提案 → 评审） |

本文主要讲第二条轴，因为它是目前唯一有可测信号的。

**这里的「进化」指：检索配置因为记录下来的结果而改变，且每一次改动都可评审。** 它不指模型每晚重写自己的提示词。

## 角色分工

这个分工是有意为之，而且和项目其它部分用的是同一套分工。

| 步骤 | 负责方 | 落在哪里 |
| --- | --- | --- |
| 回答问题 | 后端 | 确定性检索 + 可选的单发综合 |
| 给回答评分 | **人**，在工作台里 | `POST .../feedback` → SQLite `query_feedback` |
| 多步探索 | **外部 agent** | Codex / Claude Code / OpenClaw 通过 MCP，或人使用图谱、链接面板与 lint 视图 |
| 对比策略 | 后端脚本 | `backend/scripts/replay_queries.py` |
| 把证据变成提案 | 后端脚本 | `backend/scripts/propose_strategy_change.py` |
| 决定与合并 | **人**，通过 git | 一份提案文件 + 策略/配置改动 |
| 读回结果 | 后端 + MCP | `GET .../feedback`、`list_answer_feedback` |

这张表里没有任何一步需要 AgentKB 内部有 agent，而有两步必须是人。这正是重点：模型擅长提议，不擅长判断自己有没有改好。

## 闭环

```text
  应用改动                                          回答问题
  并合并 PR                                             │
        │                                                ▼
        │                                        ┌───────────────┐
        └────────────────────────────────────────│  👍 / 👎 + 原因
                                                 └───────┬───────┘
                                                         │
                       ┌─────────────────────────────────┘
                       ▼
                  记录信号
       query、answer、strategy_id、hops、vectors、
       planned、引用页面、评分
                       │
                       ▼
              回放：把记录下来的问题
              在全部策略上重跑并做差异
       ┌───────────────┴────────────────┐
       ▼                                ▼
  👍 用例：当时引用的              👎 用例：结果
  页面还能召回吗？                 真的变了吗？
       │                                │
       └───────────────┬────────────────┘
                       ▼
            提案文件：证据、确切要改的
            那一行、以及这份证据
            说明不了什么
```

## 一个闭环需要的四样东西，以及它们在哪

1. **信号** —— `query_feedback`（SQLite）。仅追加，所以「改变主意」本身也是数据。它把检索配置和评分存在一起：`strategy_id`，以及响应里的 `hops`、`vectors`、`planned`。没有这些，一个 👍 就无法归因到某个配置。
2. **记忆** —— `app/services/retrieval_strategy.py` 里的策略集合，加上 `docs/RETRIEVAL_CN.md` 里的配置项。刻意用代码而不是运行时表：**「改检索能做什么」始终是一次经过评审的改动**。
3. **回放** —— `backend/scripts/replay_queries.py`。在记录下来的问题上对比策略，报告被点赞的引用是否还在、以及每个策略的代价。
4. **闸门** —— `backend/scripts/propose_strategy_change.py` 写出可评审的 Markdown 提案，晋升就是一次普通的 git 改动。审计日志与回滚机制是同一个东西。

## 操作流程

```bash
# 0. 先确认有人评过：在工作台里点 👍 / 👎
cd backend

# 1. 当前默认策略还安全吗？（丢掉被点赞引用时退出码为 1）
PYTHONPATH=. python scripts/replay_queries.py --knowledge-base-id 1 --rating 1

# 2. 对比候选
PYTHONPATH=. python scripts/replay_queries.py --knowledge-base-id 1

# 3. 用这份证据写出提案
PYTHONPATH=. python scripts/propose_strategy_change.py --knowledge-base-id 1

# 4. 读 proposals/…md，做决定，应用改动，跑测试，开 PR
```

## 这份证据能说什么、不能说什么

这一节是让闭环保持诚实的关键，在相信脚本打印出的任何数字之前值得先内化。

**能说**

- 某个策略丢掉了人点过赞的页面。这是回归，没有余地。
- 某个策略改变了人标为差的问题的结果。这是值得人看一眼的候选——不是修复。
- 某个策略多花了链接跳数或关联页。这是代价。

**不能说**

- 某个候选**更好**。没有标准答案；「变了」不等于「对了」。
- 任何人没评过的问题。信号只覆盖人们真正问过并评判过的问题，而其中有偏向：人们倾向于只评判感觉不对的问题。
- 工作区根本支撑不了的召回。材料不在，所有策略都返回空，它们看起来一样好。

正因如此，提案脚本的默认建议是**保持现状**；只有当某个候选保留了全部被点赞的引用**且**改变了至少一个被踩的用例时，它才会提出晋升。即便如此，提案的措辞也是「值得人工看一眼」，而不是「合并它」。

## 实例（真实数字）

一个 25 页工作区上记录的反馈：6 条 wiki 评分（4 👍 / 2 👎），用 `propose_strategy_change.py` 回放全部五个策略：

| 策略 | 👍 引用保留 | 相对默认的回归 | 相对默认的新改变 | 平均关联页 | 平均跳数 |
| --- | --- | --- | --- | --- | --- |
| `auto` ← 当前默认 | 14/14 | — | — | 0.33 | 1.17 |
| `local` | **12/14** | **1** | 0 | 0.00 | 1.00 |
| `deep` | 14/14 | 0 | 0 | 0.33 | **2.00** |
| `hybrid` | 14/14 | 0 | 0 | 0.00 | 1.17 |
| `planned` | 14/14 | 0 | 0 | 0.00 | 1.17 |

细心的读者会得出什么，以及工具实际给出了什么结论：

- **保持 `auto`。** 没有任何候选改变了默认策略尚未改变过的用例，所以晋升它们什么也换不来，而 `deep` 会把链接跳数翻倍。
- `local` **相对默认策略丢掉了一个被点赞的引用**——链接扩展在挣它的成本，而这一点现在是证据而不是口味。
- `hybrid` 与 `planned` 在这里看起来一样，是因为被评分的问题措辞与作答页面很接近。这是证据本身的局限，不是对向量的判决：[RETRIEVAL_CN.md](RETRIEVAL_CN.md) 里的测量显示，向量在没有任何人评过的改写式问题上是有帮助的。

### 这个实例抓出的错误

提案脚本的第一版把每个候选和**当时的记录**比较，而不是和当前默认策略比较，于是它建议了 `deep`——因为 `deep`「改变」了两个被踩的用例，尽管默认策略同样改变了它们（那来自更早一次打分改动），而真正的差别只是多走了一跳。

这正是本文警告的「奖励作弊」失效模式，而它由本该检测它的工具产生。修复现在成了一条规则：**候选只会被记功于默认策略尚未做过的改变**，而相对默认策略的回归直接否决。值得一提的是，评审第一版提案的人必须靠读逐条明细才能发现这个问题——这也正是提案打印明细而不是打印一个分数原因。

## 失效模式与已有的对策

| 失效 | 为什么会发生 | 对策 |
| --- | --- | --- |
| **奖励作弊** | 优化对准了代理指标（引用更多、lint 更干净）而不是有用性 | 回放报告的是**被点赞引用的保留**与**哪些**用例改变，从不给出单一分数；晋升必须由人决定 |
| **漂移** | 提示词与 skill 被反复重写到不可用 | 策略集合是带测试的代码；提案是待评审的文件；回滚是 `git revert` |
| **成本爆炸** | agentic 检索每次提问 N 次工具调用 | 默认路径不加载模型；`planned` 只多一次调用；跳数与关联页数按策略设上限 |
| **不可复现** | 全 agentic 路径让回归难以归因 | 确定性核心保持默认并被测试套件覆盖；每个响应都回报 `strategy/hops/vectors/planned` |
| **溯源稀释** | 把网页材料自动摄取进 wiki | `full_text` / `excerpt` / `link_only` 由代码强制，来源元数据必填，完整第三方正文永不离开运行时目录 |
| **静默改进** | 「模型变好了」但什么都没有记录 | 任何策略改动都必须在提案里引用一份回放对比 |

## 刻意不做的事

- **后端里的 agent。** 它会重复调用方 Agent 已经做得更好的事，违反 `AGENTS.md` 里的 MCP 契约（`query_wiki` 强制 `llm.enabled=false`），并把成本、漂移与不可复现推进最难回滚的那一层。
- **自动晋升。** 即使是很小的参数改动，只有在回放证据保留全部被点赞引用时才可能不经人；那是策略决定，不是默认行为。
- **评审队列服务。** 在这个规模上，Markdown 提案文件 + git 评审就够了。当有多人并行分诊改动时，队列才值得做。
- **从点击行为学习。** 打开一个引用不等于认可；只有显式评分才被当作信号。

## 继续扩展这条闭环

按证据能支撑的顺序排列，自然的下一步是：

1. **每个问题拿到更多信号**：让评分能指明是哪个引用不对，这样回放就能按页面级保留打分，而不是按集合保留。
2. **一份冻结的评测集**：把讨论最多的记录问题提升为人工标注用例，这就把差异工具在那些用例上变成真正的打分器。
3. **知识轴的进化**：让工作由 lint 与图谱缺口驱动，进入一个研究步骤去摄取缺失的内容——同一条闭环，只是指向内容而不是策略。
